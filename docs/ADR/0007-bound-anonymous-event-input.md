# ADR 0007: 匿名イベント作成の入力を小さく制限する

Status: accepted

Date: 2026-09-01

## context

イベント作成server functionは、ログインせず共有URLを発行するため、インターネットへ公開した場合は誰でも呼び出せる。
入力の有無と日時の形は検証しているが、イベント名、主催者のひとこと、候補件数に上限がない。

上限がなければ、一回のrequestで巨大な文字列や大量の候補を送り、長いtransaction、DB肥大化、描画負荷を発生させられる。
また、タイムゾーンは文字の形しか確認しておらず、`Fake/Zone` のような実在しない名前も保存できる。

## decision

- イベント名は、前後の空白を除いた100文字以内とする。
- 主催者のひとことは、前後の空白を除いた500文字以内とする。
- 一つのイベントに登録できる候補日時は20件までとする。
- 文字数はRustのUnicode scalar value数で数える。ブラウザーの `maxlength` も早いフィードバックとして同じ数値を設定する。
- ブラウザーとサーバーで共通の入力検証を使い、サーバー側の検証を正本とする。
- タイムゾーンはブラウザー側で安全な文字形を確認し、サーバー側ではIANA databaseを持つ `chrono-tz` 0.10.4で実在も確認する。
- 上限超過は入力欄に結び付いた日本語のエラーとして返す。

100文字あれば短い集まりの名前を十分に表せる。
500文字は「ひとこと」の任意説明を保ちつつ、長文投稿欄へ性質を変えない。
20候補は人が比較できる初期MVPの範囲を保ち、First Instructionが避ける大量日時入力にも境界を置ける。

## rejected options

### 入力上限を設けない

利用者の表現を制限しない。
しかし、匿名公開APIの一request当たりの計算量と保存量を制御できず、通常の画面でも比較できない候補数を受け付けるため却下する。

### ブラウザーだけで制限する

通常操作には十分に見える。
server functionは直接呼び出せるため、改変したrequestで上限を回避できる。認可と同じく、入力検証もサーバーを正本にする。

### UTF-8 byte数で文字を制限する

DB容量との関係は直接的になる。
一方、日本語とASCIIで入力できる文字数が大きく変わり、利用者へ説明しにくい。初期MVPでは文字数で制限する。

### タイムゾーンの文字形だけを検証する

WASMへタイムゾーンdatabaseを含めずに済む。
ただし、存在しない名前を保存すると後続のiCalendar出力で時刻を正しく変換できないため、サーバーだけにdatabaseを持たせて検証する。

## consequences

- 一requestと一transactionが扱う入力を小さく保てる。
- 通常の画面では上限到達前に入力を止め、直接requestでも同じ上限を回避できない。
- 実在しないタイムゾーンが共有データへ入らず、後続の日時変換で失敗しにくくなる。
- 100文字を超える名前、500文字を超える説明、21件以上の候補を本当に必要とする利用者は、内容を短くするかイベントを分ける必要がある。
- ブラウザーの `maxlength` はUTF-16 code unitで数えるため、一部の絵文字ではサーバーの文字数と完全には一致しない。サーバー上限を越えて受理することはないが、ブラウザーが早めに入力を止める場合がある。
- IANA databaseの更新へ追従するため、`chrono-tz` の更新確認が必要になる。
